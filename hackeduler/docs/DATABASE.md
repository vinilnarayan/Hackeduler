# Database

PostgreSQL 16. The authoritative DDL is `backend/alembic/versions/0001_initial_schema.py`. Apply it with
`alembic upgrade head`. All primary keys are UUIDs (bookings and audit ids are UUID v4 generated by the app),
except `roles.id`.

## Entity overview

```
roles 1─* users 1─* bookings *─1 security_resources 1─* resource_leaves
                      │  *─1 activity_types
                      ├─* booking_resource_locks (one row per reserved working day)
                      ├─* booking_status_history (append-only)
                      ├─* booking_change_requests
                      ├─* booking_conflicts (booking_id, conflicting_booking_id)
                      └─* email_notification_logs (outbox)
holidays            audit_logs (append-only)     email_templates     application_settings
```

## Tables

| Table | Purpose | Key constraints / indexes |
|---|---|---|
| `roles` | `admin`, `requester` | CHECK name |
| `users` | Accounts. `deleted_at` marks archived (deleted) accounts; email uniqueness applies to non-deleted accounts only. `password_hash` is NULL for SSO-only users. `sso_provider_id` + `sso_subject` link an external identity. `token_version` revokes sessions | unique `lower(email)`; partial unique `(sso_provider_id, sso_subject)` |
| `sso_providers` | OIDC providers configured in the admin UI: issuer, endpoints, client id, **encrypted** client secret, claim mapping, group→role mapping, restrictions, provisioning options | unique `slug` (CHECK pattern) |
| `security_resources` | Engineer ↔ anonymous identifier (`RES-NN`, `Resource NN`); `inactive_from` (first unavailable date, scheduled or immediate) and `inactive_reason` | unique `sequence_no`, `code`, `display_name`. Never deleted |
| `activity_types` | Name, `base_duration_days` (>0), additional-days rule, active flag | unique `(name, base_duration_days)`, CHECKs |
| `holidays` | Organisation-wide holidays | unique `holiday_date` |
| `resource_leaves` | Per-resource full-day leave (`active`/`cancelled`) | CHECK `end_date >= start_date`; partial index by resource and range |
| `bookings` | Booking + **snapshot** of activity name, base duration, additional days, total duration. Status, approval, rejection and cancellation metadata, `needs_review`, `is_force_allocated`, `version` | CHECK status, range; indexes on (resource, dates), status, (requester, submitted_at), dates |
| `booking_status_history` | Every status transition (append-only) | trigger blocks UPDATE/DELETE/TRUNCATE |
| `booking_resource_locks` | One row per reserved working date: `pending`/`confirmed`/`released`, `is_forced`, `expires_at` | **partial UNIQUE `(resource_id, work_date)` WHERE active AND NOT forced**; partial lookup index; index by booking |
| `booking_change_requests` | Requester cancel/reschedule requests | partial unique: one pending request per booking |
| `audit_logs` | Immutable audit trail (JSONB previous/new values) | trigger blocks UPDATE/DELETE/TRUNCATE; indexes on booking, actor, action, created_at |
| `booking_conflicts` | Conflict register: type ∈ overlapping_booking, leave, holiday, inactive_resource, manual_override; open/resolved; resolver and timestamp | indexes on (status, created_at), booking |
| `email_templates` | Editable subject/body templates | unique `key` |
| `email_notification_logs` | Outbox and delivery log: status, attempts, next_attempt_at, last_error, sent_at | index `(status, next_attempt_at)` |
| `application_settings` | Key → JSONB admin settings (no secrets) | PK key |

## How date ranges handle non-working days

`bookings.start_date`/`end_date` are the first and last **reserved** working days. The authoritative set of
reserved days is the booking's active rows in `booking_resource_locks`. Weekends, holidays and leave days inside
the span have no lock rows, so they never block anyone. Overlap prevention is therefore a per-day uniqueness
constraint, and needs no range-overlap exclusion constraint.

## Immutability

```sql
CREATE TRIGGER trg_audit_logs_immutable BEFORE UPDATE OR DELETE ON audit_logs
  FOR EACH ROW EXECUTE FUNCTION orp_reject_mutation();
CREATE TRIGGER trg_audit_logs_no_truncate BEFORE TRUNCATE ON audit_logs
  FOR EACH STATEMENT EXECUTE FUNCTION orp_reject_mutation();
-- same for booking_status_history
```

**Production recommendation:** run the application with a dedicated, **non-superuser** role, and keep the schema
owned by a separate migration role. Superusers can bypass triggers with `session_replication_role`; the test suite
uses that only to reset its scratch database. Optionally also `REVOKE UPDATE, DELETE, TRUNCATE ON audit_logs,
booking_status_history FROM <app_role>`.

## Retention

Bookings, locks (released rows), audit logs and status history are never deleted by the application. Archive or
partition `audit_logs` by `created_at` if volume requires it.
